## 최종 목표 (북극성)
**Word 본문에서 바로** Obsidian 마크다운(과 호환되는 커뮤니티 플러그인)으로 편집한다. 작업창 에디터는 그 목표로 가는 중간 단계다. 지금까지 만든 것은 UI와 무관하게 재사용되는 **엔진**이다.
- **최종 제공 형태는 네이티브 앱**이다. 최종 사용자의 설치·실행이 npm 명령, 개발 서버나 GitHub Pages에 의존하지 않게 한다. 현재 npm/Office.js/GitHub Pages는 개발·검증용 중간 환경이다. 네이티브 호스트의 구체 기술과 설치/배포 방식 논의는 후순위로 두고 본문 편집 기반을 먼저 검증한다.
- Obsidian의 **원본 모드 / 실시간 미리보기** 전환을 편집 경험의 참고로 삼는다. 이 목표가 현재 Office.js 실험을 최종 구조로 확정한다는 뜻은 아니다.
- 엔진(재사용): Word ↔ 마크다운 변환, 사이드카(Word 전용 객체 무손실 보존), 안전장치(개수 불일치 거부, 선택 영역 확인), 수식 OMML/그림, 표, 빈 문단, 플러그인 호스트와 Obsidian API 호환 계층.
- 껍데기(교체 가능): 지금은 Office.js 작업창 + CodeMirror 6. 본문 편집으로 가려면 이 껍데기만 바꾸거나 추가한다.

### 본문 편집으로 가는 길 (확인 필요 항목 포함, 구현 전 실측할 것)
1. **블록 소스 전환(라이브 프리뷰식)**: 커서가 있는 블록만 Word 본문 안에서 마크다운 소스로 바꿔 보여 주고, 커서가 떠나면 다시 Word 객체로 렌더링한다. 2026-11-06 일반 문단 1개로 공통 SelectionChanged 이벤트 + 콘텐츠 컨트롤 + 기존 HTML/마크다운 변환기의 가능성 실험을 통과했다. 실제 키 입력/IME·실행 취소·복구·복합 객체는 미검증이다. 플러그인 스니펫의 본문 동작 방식은 별도 실험이 필요하다.
2. **작업창 에디터와 본문의 연동 강화**: 선택 영역 자동 불러오기/적용, 블록 단위 적용.
3. **네이티브 COM/VSTO 애드인(Windows 전용)**: 키 입력 후킹까지 가능하지만 Windows 데스크톱에 한정되고 설치가 무겁다. 이전에 시도했던 `WordMd` 방식. 엔진(TS)을 WebView2로 재사용하는 방식이면 이전 시도의 약점이었던 변환 정확도를 이 프로젝트의 엔진으로 해결할 수 있다. 1번의 실측 결과를 보고 결정한다.

## 번들 정리 + 코드 검토 결과 (이번 라운드)
- **메인 번들 837 kB → 357.6 kB (gzip 295 → 116.5)**: 마크다운 언어 지원(`lang-markdown` 트리), 변환기·Word 연동(`word`), 플러그인 하위 시스템(`plugins-ui`)을 첫 화면 이후 지연 로딩. 전체 전송량은 비슷하고 첫 화면에 필요한 양만 줄었다. 변환기는 첫 화면 뒤에 미리 받아 두므로 첫 클릭이 느려지지 않는다.
- **제곱으로 느려지던 구간 수정**: `parseStyleNames`가 문서 전체에 `[^{}]+` 정규식을 돌려서 입력이 2배면 시간이 4배였다(147 kB HTML에서 불러오기 11.9 s → 0.44 s, jsdom 기준). `<style>` 블록 안에서만 찾도록 바꿨다. 이제 입력 크기에 비례(589 kB에서 1.6 s).
- **사이드카 재작성 생략**: 변경이 없으면 Custom XML Part를 지우고 다시 쓰지 않는다(그림·OOXML이 든 큰 파트를 매번 다시 쓰는 비용과 불필요한 문서 변경 방지).
- 검토했지만 손대지 않은 것: 불러오기 경로의 DOMParser 5회 파싱(각각 선형, 합쳐도 작음), `math.ts`(939줄, 구조는 길지만 선형이고 테스트가 촘촘함).

- **실제 Word 실측(37쪽, 표 30, 수식 60, 그림 20, 단어 1.75만)**: 불러오기 7.8 s → 4.6 s(우리 변환 0.81~1.40 s → 0.14~0.21 s, Office.js 호스트 시간 1.5~2 s 감소). 적용은 대부분 Word의 삽입 작업이라 27 s → 16~22 s 정도로 차이가 작다.
- 실측 중 발견해 고친 버그: (1) 마크다운 언어 조각을 못 받았을 때의 안내 문구가 `Office.onReady`에 덮어써지던 것, (2) Word가 `getOoxml` 호출마다 새 `rsid`/`paraId`를 넣어서 표·떠 있는 개체가 있는 문서에서는 사이드카 재작성 생략이 동작하지 않던 것(변경 없는 항목은 기존 값을 유지하도록 정규화).

## 적용 정확성 수정 (완료, `apply-fixes`)
- **큰 문서 적용 시 문단이 사라짐(771 → 741)**: 증거. 사라진 것은 **내용이 있는 문단이 아니라 빈 문단뿐**이다. 큰 문서는 표 뒤 빈 문단 30개(diff로 확인), 혼합 문서는 표 뒤 빈 문단 1개, 간격 시험 문서(35문단)는 빈 문단 13개 전부(문장 사이 1개·연속 3개·제목 앞·목록/그림/떠 있는 개체/수식 뒤·표 뒤·문서 끝 3개)가 사라졌다. 가설 (ii)(원본 빈 문단이 마크다운에 아예 나타나지 않음)이 원인이고, (i)(`next.getPrevious().delete()`)은 부분적이다: 그 줄을 끄고 시험하면 혼합 문서는 14문단이 유지되지만 표 바로 뒤에 문단이 없던 표는 불필요한 빈 문단이 생긴다(35 → 24). 즉 표지 문단 삭제는 맞는 동작이고, 빠진 정보는 마크다운에 있어야 했다.
- **수정**: 빈 문단 표지(`<!-- word:blank [n=N] -->`, README '빈 문단과 반복 적용'). 표만 사이드카 플래그로 처리하지 않고 모든 최상위 빈 문단을 한 가지 방식으로 다룬다. 이전 마크다운은 그대로 적용된다(시험: 표지를 지운 마크다운 → 이전과 같은 22문단).
- **`getHtml`의 가짜 빈 문단**: 선택 영역이 마지막 문단 표지를 포함하면 빈 문단이 하나 더 붙는다(문서 끝 빈 문단 3개 → HTML에 4개). 보정하지 않으면 적용할 때마다 문단이 하나 늘었다(35 → 36). Office.js가 센 끝의 빈 문단 수와 비교해 정확히 1개 많을 때만 뺀다.
- **적용 직후 한 번 더 적용하면 `GeneralException`**: 증거. `OfficeExtension.config.extendedErrorLogging = true`로 `debugInfo.errorLocation = "Range.getHtml"`, `statement = "selection.getHtml();"`(안전장치가 현재 선택 영역을 읽는 첫 문장). 첫 적용 뒤 선택이 문서 맨 앞의 **삽입점**(`sel 0-0 type=1`)으로 접혀 있었고, Word는 접힌 선택의 `getHtml`에서 `GeneralException`을 던진다. (정상이라 해도 `insertHtml(replace)`는 낡은 내용을 남긴 채 새 내용을 끼워 넣을 뻔했다.)
- **수정**: (1) 적용 끝에서 영역 전체를 다시 선택(경계 문단을 추적(`trackedObjects`)해 두었다가 그 사이를 선택. `insertHtml`이 돌려주는 범위나 시작점 앵커는 객체로 문단을 바꾸면 줄어들거나 끝으로 이동해서 쓸 수 없었다 — 첫 시도에서 떠 있는 그림이 2개, 3개로 늘었다). 문서 끝까지면 마지막 문단의 `Whole` 범위를 써야 마지막 문단 표지까지 포함된다(`Content.End`로 확장하면 1 모자람). (2) 선택이 비면 안내 메시지로 중단. (3) 선택이 마지막으로 불러오거나 적용한 영역(문단 텍스트의 지문)과 다르면 확인을 묻는다.
- **인수 시험(실제 Word)**: 혼합/큰/간격 문서에서 적용 3번 연속이 같은 문서(문단 덤프 동일, 개수 동일, 예외 없음), 적용 → 에디터 수정 → 적용 → 불러오기가 수정본을 돌려줌, 적용 1번을 되돌리는 데 Ctrl+Z 2번(전과 같음), 실행 취소 직후 적용은 확인을 묻고 '바꾸기'를 누르면 기대한 상태, 실행 취소 + 다시 실행 뒤 적용은 확인 없이 같은 상태, 커서만 있는 선택은 안내 메시지로 중단하고 문서 불변, 다른 영역을 선택하면 확인 → '취소'에서 문서 불변, 문단 3~9만 선택한 부분 영역 적용 3번도 같은 문서·같은 선택, 표 줄을 지운 마크다운은 여전히 거부.
- 남은 것: 목록·표 칸 안의 빈 문단과 스타일이 있는 빈 문단(빈 제목 등)은 표지 대상이 아니라 여전히 사라진다. 적용 뒤 셀 안/떠 있는 개체로만 이루어진 영역을 선택하는 경우의 `getHtml` 가짜 빈 문단 보정은 일반 문단 영역에서만 확인했다.

## 검토에서 나온 수정과 남은 의심 (review-fixes)
- 수정·검증됨(실제 Word, main 대비): ① 사이드카를 선택 영역 기준으로 정리하던 것을 문서 전체 보존 정책으로 변경(긴 LaTeX 수식 그림이 다른 영역을 불러온 뒤에도 편집 가능), ② 떠 있는 개체·표 삽입 실패를 더 이상 성공으로 보고하지 않음(main은 "적용 완료"였고 도형 1→0, 표 1→0이 조용히 사라짐).
- **실패 경로의 실행 취소가 길다**: 삽입이 실패한 적용은 Ctrl+Z가 5~6번 필요하다(정상 적용은 2번). 안내 문구를 "여러 번"으로 바꿨다.
- **미확정 의심**: 일괄 처리가 일부 실행된 뒤 실패하면, 한 건씩 재시도하는 루프가 이미 실행된 필수 작업(예: 표 삽입)을 다시 실행할 수 있다. 수식 삽입을 일부러 실패시켰을 때 문서가 16 → 22 문단으로 늘었고(main과 브랜치 모두), 표 셀 문단 수와 맞아 표가 중복 삽입됐을 가능성이 있다. 정상 경로는 해당 없음. 확인하려면 그 상태의 문단을 덤프해 본다. 확인되면 일괄 실패 시 필수 작업은 재시도하지 않고 바로 실패 처리하는 것이 안전하다.
- 이 브랜치에서 실행하지 못한 것: 대형 문서 시간 측정과 대형 문서 반복 적용 재확인, 정상 적용의 실행 취소 단계 재측정.

- **사이드카 자동 삭제 중단**: 현재 선택 영역에 없는 항목도 문서의 다른 영역에 남아 있을 수 있다. 기존 90일 만료·16 MiB 초과 삭제 정책은 전체 참조를 확인하지 않아 긴 수식의 LaTeX를 잃을 수 있었다. 문서 전체 참조를 안전하게 확인하는 정리 기능이 생길 때까지 모든 원본을 유지한다. 사용 시각 갱신과 변경 없는 Custom XML Part 재작성 생략은 유지한다. 그 대가로 불필요한 항목이 누적될 수 있다.
- **누락 원본 사전 거부**: `renderWithSidecar`의 `missing`을 Word 연동 함수에서 검사한다. 이미지·필드 등의 원본이 없으면 `insertHtml`과 사이드카 저장 전에 중단한다. UI가 문서 교체 후에 실패를 알리던 경로를 막았다.
- **일괄 실패 시 재실행 제거**: 개체 삽입·표 뒤 문단 삭제·빈 문단 복원·영역 선택은 한 번만 실행한다. 실패하면 즉시 오류와 실행 취소 안내를 반환한다. 모의 Office 큐에서 표 삽입/문단 삭제 이후 수식이 실패하는 경우를 재현해 중복 실행이 없음을 검증했다. 앞서 기록한 실제 Word 16→22문단 현상 자체는 이번에 재측정하지 않았다.
- **선택적 스타일 적용 분리**: 객체 복원 뒤 별도 배치로 실행하고 실패 시 안내한다. 실패한 배치는 재시도하지 않으므로 일부 스타일이 적용되지 않을 수 있다. 스타일이 있는 문서에서는 쓰기 배치가 하나 추가되며 실행 취소 횟수 재측정이 필요하다. 영역 경계 추적은 성공/실패 모두 `finally`에서 해제한다.
- 검증: `npm test` **372개 통과**, `npm run build`(타입체크 포함) 통과, `git diff --check` 통과. 새 Office 큐 테스트는 수정 전 코드에서 9개 중 8개가 실패하고 수정 후 전부 통과한다. 오래된 긴 수식과 종전 용량 상한 초과 원본 보존도 검사한다. 실제 Word·대형 문서 측정은 아직 수행하지 않았다.

## 실제 Word 자동 인수 시험 (2026-11-06)
- 실행: `npm run test:word`. COM으로 시험 전용 Word 문서를 열고 실제 작업창의 Office.js에서 원본 함수를 호출한다. 화면 좌표/키보드 조작 없이 실행되며 시험 종료 시 문서·서버·고유 GUID 임시 등록을 정리한다. 상세 설정은 `scripts/word-host/README.md`, 실측은 `docs/testing/2026-11-06-word-host.md`.
- **통과**: 표·수식·떠 있는 도형·빈 문단·인용 스타일 혼합 문서 3회 연속 적용과 마크다운 왕복, 누락 원본 사전 거부(본문/사이드카 불변), 100일 지난 221자 LaTeX 그림을 둔 채 다른 영역 불러오기와 원본 재확인.
- **실패 주입 통과**: 실제 Word에 잘못된 수식 OOXML을 보내 `InvalidArgument`를 발생시켰다. 이미 복원된 도형/표는 각 1개 유지하고, 도형·표·수식 삽입 호출은 각각 1회였다. 스타일 속성 설정에 존재하지 않는 이름을 보내면 경고를 반환하고 객체를 보존했다.
- **실행 취소 실측**: 스타일 없는 정상 적용 2단계, 인용 스타일 있는 정상 적용 3단계, 위 수식 실패 경로 2단계에서 본문 텍스트·표/도형/수식 수가 복구됐다. 모든 실패 경로가 항상 2단계라는 뜻은 아니다.
- **대형 합성 문서**: Office.js 기준 300문단, 표 30개, 수식 60개, 마크다운 40,108자. 불러오기 2.02초, 적용 3.59/3.64/3.81초, 세 번 모두 문단 텍스트와 객체 수 유지. 일반 그림을 넣지 않은 별도 문서로, 과거 37쪽 문서와 성능을 직접 비교하지 않는다.
- 재사용 명령으로 전체 시험 재실행 및 자동 정리까지 확인. 기존 372개 단위 테스트·타입체크·빌드도 통과.
